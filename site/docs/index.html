ARDGuard documentation

From ranked candidates to an explainable decision.

Start with the offline demo, then choose the integration surface that fits your caller. Discovery ranks. Providers establish facts. Requirements define eligibility. ARDGuard selects or fails closed. Your runtime owns invocation.

60-second quick start

Install the current public Beta 4 and run the offline demo:

python -m pip install ardguard==0.1.0b4
ardguard demo

Expected output from the real command:

ARDGuard offline demo (illustrative)
rank 1: relevant but capability-ineligible
rank 2: eligible
top-ranked-only validation: ABSTAIN
ARDGuard: SELECT urn:air:example.org:tool:rank-two
reason: selection.fallback_to_lower_ranked_eligible
invocation: NOT PERFORMED

Payoff: ARDGuard preserved the discovery order and selected the first candidate that was actually eligible. It invoked nothing.

Concepts

Relevance

The discovery backend answers which resource looks useful and supplies the original rank or score. ARDGuard does not recompute it.

Facts

Facts are typed observations bound to a candidate and provider identity. A fact can be available, unavailable, indeterminate, or an operational error. A caller cannot submit eligible=true.

Requirements

A task states what must be true: a capability, applicable evidence, an available credential category, authority limits, or another bounded fact type.

Eligibility

ARDGuard evaluates every mandatory requirement for each candidate. Satisfied, unsatisfied, indeterminate, and error remain distinct.

Typed uncertainty

A provider unavailable state remains uncertainty. A provider operational error remains an error. Neither silently becomes a negative fact or a pass.

Fallback

When rank #1 is ineligible and rank #2 is eligible, fallback selects rank #2. It does not reorder the eligible candidates.

Invocation

ARDGuard returns a decision. The caller retains runtime authorization, approval, connection, and invocation.

Integrations

ARD v0.91

Feed a completed ARD SearchResponse through the native adapter. Optional search fields remain optional, returned order is preserved, and unknown extension terms are retained without semantic reinterpretation.

ardguard evaluate \
  --adapter ard \
  --discovery-response discovery.json \
  --task task.json --policy policy.json --facts facts.json

hf-discover

The pinned workflow preserves hf-discover's ordering, scores, metadata, and opaque fields. Eligibility is evaluated separately.

hf-discover search "find a weather tool" --json > discovery.json
ardguard validate --kind hf-discover discovery.json
ardguard evaluate --adapter hf-discover \
  --discovery-response discovery.json \
  --task task.json --policy policy.json --facts facts.json

MCP

The MCP provider is experimental and read-only. It can establish facts from initialization and tools/list; it never calls a tool. A common boundary is:

ranked MCP candidates
        ↓
verified capability / access facts
        ↓
ARDGuard eligibility + fallback
        ↓
native runtime authorization and invocation

Providers

A FactProvider establishes candidate facts. It cannot return a FinalDecision, select a candidate, or invoke a resource.

  • Installed does not mean trusted.
  • Discovered does not mean enabled.
  • Enabled does not authorize every fact namespace.
  • Provider ID, version, and permitted fact types are policy-bound.
  • Provider failure becomes an explicit operational-error fact.

Entry-point plugin discovery is opt in. Enabled provider Python code is part of the application's trust boundary.

Security model

ARDGuard protects the final-selection boundary; it is not an identity provider, authorization backend, registry, attestation issuer, or invocation runtime.

  • Missing mandatory facts never silently pass.
  • Operational failure is not cryptographic invalidity.
  • Evidence for artifact A cannot authorize artifact B.
  • Relevance scores are never promoted into trust facts.
  • Provider identity and namespace authority are enforced.
  • Core offline mode makes no implicit network calls.
  • ARDGuard never installs or invokes selected resources.

Runtime authorization still applies. A SELECT result means the candidate satisfies the configured eligibility contract. It is not permission to bypass OAuth, RBAC, approval, or native runtime controls.

Python API

from ardguard import FactSet, Policy, TaskContract, evaluate
from ardguard.adapters import parse_search_response

decision = evaluate(
    candidates=parse_search_response(discovery_response),
    task=TaskContract.from_mapping(task_document),
    policy=Policy.from_mapping(policy_document),
    facts=FactSet.from_mapping(fact_document),
)

if decision.outcome.value == "SELECT":
    print(decision.selected_candidate_id)
    # Your caller still owns authorization and invocation.

The v1 API is the supported deterministic path. The generic v2 kernel is experimental and versioned separately.

DecisionReceipts

A receipt makes the inputs and per-requirement result auditable without signing or invoking anything. Beta 4 receipts contain:

  • task, candidate-set, and policy hashes;
  • provider identities and versions;
  • fact hashes;
  • per-requirement verdicts and reason codes;
  • selected candidate and software version;
  • a deterministic receipt hash.

The receipt is content-addressed, not cryptographically signed. Use the Explorer's provenance view to inspect a complete receipt.

Operational privacy: a production receipt can expose candidate identities, ranks, policy requirements, provider identities, and provenance. Keep it inside the operator's audit boundary unless it has been reviewed and appropriately redacted. The public Explorer contains synthetic data only.

Build a provider in 15 minutes

This provider supplies deployment-region facts without changing ARDGuard core:

from ardguard import Fact, FactOperationalState

class RegionProvider:
    provider_id = "example.region-provider"
    provider_version = "1"
    supported_fact_types = frozenset({"deployment.region"})

    def __init__(self, regions):
        self.regions = dict(regions)

    def collect(self, candidate, task, requirements, context):
        del task, requirements, context
        region = self.regions.get(candidate.resource_id)
        state = (
            FactOperationalState.AVAILABLE
            if region is not None
            else FactOperationalState.INDETERMINATE
        )
        return (Fact(
            fact_id=f"region:{candidate.resource_id}",
            candidate_id=candidate.resource_id,
            fact_type="deployment.region",
            provider_id=self.provider_id,
            provider_version=self.provider_version,
            state=state,
            value=region,
            provenance={"source": "configured-control-plane"} if region else {},
        ),)

Policy must separately authorize example.region-provider@1 for deployment.region. Loading a package never grants trust.

Why not just filter?

Filter:
candidate A → blocked

ARDGuard:
candidate A → ineligible
candidate B → eligible
candidate C → indeterminate

SELECT candidate B

A boolean filter can remove a candidate. ARDGuard preserves the original rank, evaluates the candidate set, keeps typed uncertainty, returns a deterministic fallback, and explains the decision.

Why not just a trust score?

A trust score can be useful as one observation. It does not replace task-specific requirements.

A resource can be acceptable for a read task but exceed authority for a write task. Its evidence can be authentic for version 1.2 while the task requires version 1.3. ARDGuard keeps those facts separate, binds them to the exact resource, and composes them for the current task.
